# 定制工作台

把使用者真正要做的判断和推进的工作，转化为一个可运行、可追溯、可继续修改的定制工作台。不要套用统一模板，也不要把「展示更多数据」误当成完成。

## 交付结果

根据用户授权和任务范围，交付以下内容：

1. 经用户确认的 `workbench-spec.json`，记录目标、组织方式、视图、字段、真源、动作、权限和验收场景。
2. 在目标项目中可运行的工作台，或用户明确只要设计时交付可实施规格。
3. 数据来源与写回边界，明确什么是真源、快照和派生数据。
4. 实际验收证据，包括关键操作、桌面/移动端视觉检查和用户反馈。

## 不变量

1. **先确定工作，再设计界面。** 首先识别工作台帮助谁做什么判断、推进什么工作、减少什么遗漏；配色和版式随后决定。
2. **一人一型。** 导航、层级、字段和视图必须来自当前使用者的工作，不得照搬另一个使用者的专属工作台或保险示例。
3. **工作台不是真源。** 默认把工作台视为可操作快照；不得编造进度、数据、截止时间或完成状态。
4. **先确认契约，再实施。** 问题契约和工作台契约未确认前，不进入完整实现；低保真草图可以用于澄清。
5. **渐进式访谈。** 每轮只问 1～3 个会改变设计的高杠杆问题；已有材料能回答的内容先自行提取，不让用户重复说明。
6. **视图服从问题。** 客户、项目、案件、资产和时间周期需要不同组织方式；同一工作台也可混合视图，但每个视图必须回答一个明确问题。
7. **身份合并有证据。** 多次会话、笔记或文件只有在身份键或用户确认支持时，才能归入同一人物/项目；不能只凭相似名称自动合并。
8. **敏感信息最小化。** 客户、健康、保单、财务等数据默认私密、本地、最小权限；示例和测试不得使用真实个人资料。
9. **写操作单独授权。** 打开文件或链接可以按已确认设计执行；改写真源、运行有副作用的命令、自动通知或对外发布前必须获得对应授权。
10. **尊重现有项目。** 先读项目真源、规则、当前技术栈和运行态；只在必要位置新增或改动，不用新框架重写可工作的系统。

## 路由

- **新建工作台**：从访谈和问题契约开始，确认后实现最小可用版本。
- **改造现有工作台**：先审计当前代码、数据与使用问题，只补问影响改造的缺口，保留已经有效的路径。
- **只做规格**：仅当用户明确不要实现时停止在已确认的 `workbench-spec.json` 和实施说明。
- **仅打开现有工作台**：不要使用本 Skill，按目标项目已经存在的入口或启动说明处理。

## 核心流程

### 1. 建立问题契约

先读取用户给出的对话、文件、表格、现有页面和项目规则。提取已知事实，再按 [访谈指南](references/discovery-interview.md) 补齐会改变设计的缺口。

至少确认：

- 使用者和工作场景；
- 工作台要支持的核心决定、动作与成功证据；
- 首要组织单元及层级；
- 最容易漏掉、延误或判断错误的环节；
- 数据真源、更新节奏、隐私和写回权限。

用一段短摘要回述「为谁、解决什么、如何算有用、暂不处理什么」，请用户确认。存在关键歧义时停止在这里。

### 2. 设计工作台契约

根据 [信息架构与视图选择](references/information-architecture.md) 决定：

- 左侧导航按人物、项目、案件、资产、时间周期、业务区域或混合方式组织；
- 是否需要父子层级，例如「客户 → 第 1 次/第 2 次/第 3 次沟通」；
- 每个视图回答的问题、显示字段、来源和可执行动作；
- 列表、详情、看板、时间线、表格、指标、日历或周期复盘中的最小组合。

把结论写入 `workbench-spec.json`。以 [契约模板](assets/workbench-spec.example.json) 为起点，并参考 [JSON Schema](assets/workbench-spec.schema.json)。运行：

```powershell
node scripts/validate-workbench-spec.mjs <workbench-spec.json>
```

向用户展示信息架构、关键页面、真源和动作边界，不展示无关的实现细节。用户确认后再进入构建。

### 3. 明确数据与权限

读取 [数据、安全与身份归并](references/data-and-safety.md)，为每个字段标明来源、权威级别、刷新方式和敏感等级。明确：

- 哪些数据只读；
- 哪些动作会写回真源；
- 哪些链接打开本地文件、内部页面或外部搜索；
- 身份如何匹配，多次沟通如何串联；
- 数据缺失、冲突、过期时页面如何显示。

不接受「先做出来再说」作为敏感数据或自动写回的授权。

### 4. 实施最小可用工作台

按 [构建与验收](references/build-and-acceptance.md) 选择最小技术路径：

- 现有项目：沿用当前框架、组件库、数据接口和启动方式；
- 本地静态快照：优先 HTML/CSS/JavaScript；
- 需要持续监听本地文件：使用最小本地服务或项目已有机制；
- 需要数据库/API：先验证凭证、权限、失败态和写回边界。

先完成一个贯通的主流程，再扩展次要页面。必须实现加载、空数据、错误、过期和无权限状态。操作型界面保持安静、紧凑、可扫描；不要做营销首页、装饰性大标题或卡片套卡片。

### 5. 验收与迭代

用契约中的真实场景逐项验收：

- 使用者能否快速找到当前最重要的对象；
- 能否看清状态、证据、风险和下一行动；
- 能否打开正确的文件/详情/搜索或执行已授权动作；
- 页面是否准确显示缺失、冲突和过期信息；
- 桌面端与移动端是否无重叠、截断和布局漂移。

向用户询问「哪些信息不够、哪些太多、组织方式是否顺手、视觉风格哪里不满意」。把反馈映射到字段、视图、导航或视觉方向，做定点修改并回归主流程，不因单个视觉意见重做全部架构。

## 完成标准

只有同时满足以下条件才可报告完成：

- 问题契约和工作台契约均获确认；
- `workbench-spec.json` 校验通过；
- 工作台的主流程可以实际运行；
- 数据来源、更新时间和写回权限可见且真实；
- 至少一个主场景和一个缺失/错误场景通过；
- 视觉检查覆盖用户的主要设备；
- 用户完成一次信息架构与视觉满意度复核。

如果当前只完成规格、原型或结构校验，必须明确写出验证等级和仍缺的证据。

## 示例边界
