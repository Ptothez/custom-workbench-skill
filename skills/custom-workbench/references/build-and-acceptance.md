# 构建与验收

在工作台契约获确认后读取本文件。

## 技术路径

1. 先审计目标目录的规则、真源、代码、数据接口和启动脚本。
2. 已有应用沿用现有框架与组件库，避免无关重构。
3. 只展示本地快照且无需自动刷新时，使用最小静态实现。
4. 需要监听本地文件时，采用项目已有机制；没有时再增加最小本地服务。
5. 需要 API/数据库时，先验证权限、速率、错误处理和脱敏，再接入界面。
6. 先打通「进入对象 → 理解状态 → 执行下一步」的主流程，再做次要模块。

## 操作型界面约束

- 默认采用克制、工作导向、易扫描的布局，不做营销落地页。
- 侧栏用于稳定导航，主区域用于当前对象或任务；筛选器和动作靠近其作用范围。
- 使用项目已有图标库；新项目优先使用 Lucide 图标，不手绘替代图标。
- 按钮使用清晰命令，模式使用分段控件，二元设置使用开关/复选框。
- 卡片只用于独立重复项、模态框或真正需要边界的工具；不做卡片套卡片。
- 紧凑面板使用紧凑字号；不要用超大标题占据工作空间。
- 表格长文本使用省略与完整提示，列宽可预测，横向滚动限制在表格容器内。
- 固定格式控件使用稳定尺寸，加载、空态和标签变化不能推动整体布局。
- 不用装饰性渐变球、虚构指标或无含义的百分比填满页面。

## 必备状态

实现并验证：

- 加载中；
- 无数据；
- 部分缺失；
- 数据过期；
- 权限不足；
- 操作失败与重试；
- 成功但无变化；
- 身份或来源冲突。

## 验收场景

每个场景使用「前提 → 操作 → 可观察结果」描述。例如：

```text
前提：客户有三次沟通记录，最近一次缺少下一行动。
操作：从客户列表进入该客户。
结果：时间线按日期显示三次沟通，并把缺少下一行动标为待处理；不会编造行动或截止日期。
```

至少覆盖：

1. 一个最常用主流程；
2. 一个缺失/冲突/无权限场景；
3. 一个打开文件、详情或搜索的动作；
4. 若存在写回，再覆盖确认、成功和失败。

每日重点／行动判断追加 `decision-and-refresh.md` 的业务案例：重点是否选对、来源遗漏是否可发现、确认计划能否显示和保留、完成任务是否退出、跨日／来源／模型失败如何恢复。结构、格式、点击、视觉和业务选择分层验收。

## 视觉与交互检查

- 使用真实浏览器打开实际运行页面，不以源代码检查替代。
- 检查用户主要桌面尺寸，并至少检查一个窄屏尺寸；默认可用 `1440×900` 与 `390×844`。
- 截图检查首屏、长列表、展开层级、弹窗和错误态。
- 验证文字不重叠、不截断关键含义、控件不跳动、导航可返回。
- 实际点击主路径，确认链接、筛选、展开、保存和刷新符合契约。
- 若使用可视化或 Canvas，检查实际像素非空并在不同尺寸正确取景。

## 用户复核

实现后只问能驱动修改的问题：

- 你是否能在一分钟内找到最该处理的对象？
- 哪些信息太多，哪些信息不足？
- 当前组织方式是否符合你平时找资料和推进工作的顺序？
- 哪个视觉细节妨碍扫描或让你不愿长期使用？

根据反馈定位到导航、字段、视图、动作或视觉方向。结构问题先于装饰问题；局部问题做局部修正，并回归已经通过的主流程。
